IEC104 Slave Integration Application

Bridge that consumes backend reported-data updates (WebSocket) and exposes them as an IEC60870-5-104 slave with spontaneous telemetry, periodic measurements, GI responses, and command forwarding.
IEC104 Slave Backend WS Consumer Backend REST Caller Excel-driven IOA Map GI + Spontaneous + Periodic
Documentation for the IEC104 slave bridge in this bundle (Iec104_slave.py + Iec61850Integration). This is intentionally scoped to this application’s interaction with the backend driver and the provided Excel mapping.
Context guardrail: this is not a generic IEC104 framework. It assumes backend message shape from /reported_data and an Excel sheet containing IEC104 IOA/type mappings.
Network interfaces
IEC104 slave: 172.16.1.120:2404
Backend WS: ws://localhost:8000/reported_data
Backend REST: http://localhost:8000/service
What this application does
  • Creates an IEC104 slave endpoint for IEC104 master clients.
  • Consumes backend live updates from /reported_data WebSocket.
  • Maps backend attributes to IEC104 IOAs using flattened_dataset.xlsx.
  • Emits spontaneous ASDUs for SP/DP types; caches MV types for periodic emission.
  • Serves GI by sending current values for all mapped IOAs.
  • Forwards incoming IEC104 commands to backend Command service via REST.

Context-only usage note
This implementation assumes a very specific runtime environment: backend driver on localhost:8000, an Excel sheet containing IEC104 mappings, and the IEC104 DLL wrapper present on the host OS. Treat it as an integration bridge, not a general-purpose library.

Backend dependency
The bridge is a backend client. It does not speak MMS. It depends on:
  • WebSocket /reported_data for live updates.
  • REST /service for forwarding commands.

Telemetry handling (backend → slave → master)
Backend updates arrive via WebSocket /reported_data and are processed by _process_reported_data:
  1. Each nested payload is flattened to dotted keys, prefixed with base_da.
  2. For each flattened key/value, change-detect vs _last_values.
  3. Find matching Excel rows where DataAttribute == flat_key and IEC104_IOA is present.
  4. Build InformationObjects based on IEC104_Type: SP (single point), DB (double point), MV (measured value).
  5. Non-MV types are immediately packaged into spontaneous ASDUs with CP56Time2a timestamp and enqueued.
  6. MV values are cached in _measurement_values and sent periodically (default 5 seconds) as periodic ASDUs.
General Interrogation (GI) behavior
GI is handled by CS101_InterrogationCallback when qoi == 20. The application sends:
  • ACT_CON (activation confirmation)
  • Interrogated-by-station ASDUs containing all mapped IOAs (grouped by IEC104_Type)
  • ACT_TERM (activation termination)
ASDU batching: If an ASDU becomes full (CS101_ASDU_addInformationObject returns false), the current ASDU is enqueued, a new ASDU is created, and the IO is added again.
IEC104 command handling (master → slave → backend)
Incoming IEC104 commands are handled in CS101_ASDU_Callback:
  1. Extract IOA and cmd_value from the received ASDU.
  2. Lookup rows where IEC104_IOA_CMD == IOA.
  3. For each match, compute backend control reference: command_ref = DataObject.replace("ST","CO").
  4. If the command is a SELECT: append $SBOw; otherwise append $Oper.
  5. Call backend REST /service with name="Command", parameters {ref, ctlval} and host=IED.
Note: Cancel is not generated by this application for IEC104 commands; only Select and Operate are forwarded.
Cause of transmission used
  • CS101_COT_SPONTANEOUS for non-MV backend changes.
  • CS101_COT_PERIODIC for periodic MV packets (every 5s).
  • CS101_COT_INTERROGATED_BY_STATION for GI response.

Timestamp and quality usage
For SP/DB spontaneous packets, the bridge reads:
  • q from backend nested payload (default 0)
  • t from backend nested payload (ms epoch; default now)
MV periodic packets use quality 0 and current timestamp (now).
Startup and steady-state
  1. Load slave_config.json (ip/port).
  2. Load flattened_dataset.xlsx and filter rows where IEC104_IOA exists.
  3. Create CS104 slave instance, register handlers.
  4. Start slave (listen on 172.16.1.120:2404).
  5. Schedule periodic measurements task (default: 5s).
  6. Connect to backend WebSocket and start processing updates.
Data and command paths
  • Telemetry: backend WS → Excel lookup → IOA/type → spontaneous ASDU → master.
  • Measurements: backend WS → cache MV by IOA → periodic ASDU (5s) → master.
  • GI: master → interrogation callback → Excel group by type → ASDUs → master.
  • Commands: master IOA_CMD → Excel lookup → backend /service Command call.
Duplicate / flood control behavior
The bridge only sends spontaneous updates when a flattened key’s value changes compared to _last_values. This is your primary flood control. Measurements are sent periodically regardless of change (from _measurement_values cache).
Public entrypoint
The entry script Iec104_slave.py does:
  • Create Iec104Slave()
  • Await start() to start listening and schedule periodic MV
  • Await back_end_connect() to begin backend subscription loop
