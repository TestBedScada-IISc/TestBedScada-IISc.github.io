IEC61850 Client RESTFul server driver

FastAPI + multi-device orchestration + protocol client wrapper. Real-time monitoring via WebSockets. Control via REST.
REST WebSocket Streams Multi-Device RCB / Reporting Commands
This package exposes IEC 61850 client capabilities through a REST + WebSocket server. It is organized as a small stack: a protocol client library (single device), an application orchestrator (multiple devices), and an integration server (FastAPI).
Boundaries: Library → Application → Server.
High-level flow
  1. Start FastAPI server.
  2. Server creates a single application instance (singleton for the process).
  3. Application creates one client per host from JSON config.
  4. Each client connects in its own background thread.
  5. RCBs enabled automatically on connect; reports stream to subscribers.
  6. External callers use REST for reads/commands and WS for live streams.
Component map
IEC61850ClientLibrary Single-device protocol client wrapper.
IEC61850ClientApplication Multi-device orchestration + cache + callbacks.
APIIntegrationServer FastAPI REST + WS interface for external systems.
External interfaces
  • WS: /reported_data live reported values
  • WS: /connection_status live state changes
  • WS: /log_command service-call telemetry
  • REST: /service, /dataset, /command, /manage, /connections_status
Runtime properties
  • Thread-per-host connection startup (daemon threads)
  • Callback-driven report updates
  • Central caches for reported data, dataset model, connection status
  • Broadcast fan-out to multiple WebSocket subscribers

Supporting files

Entry + Config
FastAPI entry script (iec61850.py)

This file is responsible for starting the FastAPI server process. It instantiates the server wrapper and runs it under Uvicorn. The server internally creates exactly one application instance for the process, which then spins up multiple device clients (one per configured host) using background threads.

Purpose
  • Start Uvicorn
  • Create APIIntegrationServer instance
  • Expose REST and WebSocket interfaces
  • Trigger application connect during FastAPI lifespan startup
Expected behavior: on process start, the server begins connecting to all configured hosts automatically. External systems then consume live streams or issue service/command calls.
Configuration file (config.json)

The configuration defines each target host, its IP/port, and reporting subscriptions (RCBs). The application loads this file at startup and creates one client instance per host.

Conceptual schema
{
"<host_name>": { "ip": "<ip>", "port": 102, "rcbs": [ ... ] }
}
Each rcbs entry maps an RCB reference to optional parameters like trg_opts and intg_pd.
Reality check: config correctness decides whether the system “just works” or “mysteriously does nothing”. Keep this file version-controlled and reviewed.
End-to-end threading and data flow
Threading model
  • IEC61850ClientApplication.connect() starts a daemon thread per host for connection.
  • Protocol library may also maintain internal reconnect behavior.
  • FastAPI runs on an async event loop, broadcasts to WS subscribers from callbacks via thread-safe scheduling.
Data flow
  1. Library receives a report → decodes values.
  2. Application updates _reported_data[host].
  3. Server callback schedules broadcast to /reported_data subscribers.
  4. Consumers receive JSON updates in real-time.

IEC61850ClientApplication

Multi-device orchestration
Purpose
  • Load device configuration from config.json.
  • Create and own one library client per host.
  • Centralize caches: reported data, dataset models, connection status.
  • Auto-enable RCBs on connect and reconnect.
  • Offer a simple app-facing API for service calls and commands.

APIIntegrationServer

FastAPI wrapper
Purpose
  • Expose orchestration layer via REST and WebSockets.
  • Broadcast report and status changes to multiple subscribers.
  • Provide a generic service endpoint and a command endpoint.
  • Provide simple start/stop host management.
  • Offer command logging stream (/log_command) for UI/audit/telemetry.

Operational notes
  • CORS open is fine in a lab. In anything else, it’s an invitation.
  • /service JSON in query works but is brittle (escaping breaks clients easily).
  • WebSocket handlers expect clients to send some text periodically to keep the receive loop alive.

Usage

Quick reference
Start the server
  1. Update config.json with hosts, IP, port, and RCB definitions.
  2. Run the startup script (Uvicorn entry).
  3. Wait for hosts to connect (status stream will show it).
Consume data (WS)
  • Connect to /reported_data for live values.
  • Connect to /connection_status for state changes.
  • Connect to /log_command to observe service calls.
Read dataset model
REST: GET /dataset
Returns cached dataset structures discovered during RCB setup.
Execute control command
REST: POST /command?host=<host>
Body example:
{
  "object_ref": "LD0/CSWI1.Pos",
  "ctlVal": 1,
  "test": false,
  "check": false
}
Responsibility boundaries
  • IEC61850ClientLibrary: protocol correctness, decoding, control writes.
  • IEC61850ClientApplication: multi-host lifecycle, caching, config-driven setup.
  • APIIntegrationServer: external interface, WS fan-out, REST routing, process lifecycle.
