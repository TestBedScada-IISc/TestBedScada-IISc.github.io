Event List Interaction Application

FastAPI event list UI that consumes backend reported data via WebSocket, generates event records, persists them to MongoDB, and streams live events to the browser.
FastAPI UI Server Backend WS Consumer MongoDB Persistence Excel-driven Event Filter Live Broadcast
Documentation for Event_list.py and its bundle files. This is intentionally scoped to this application’s usage of the backend driver and this Excel sheet.
Context guardrail: this is not a generic event engine. It assumes the backend driver’s /reported_data message shape and the presence of Description + Event_list in the Excel mapping.

What this application does
  • Runs a FastAPI UI server for viewing SCADA/IEC events.
  • Subscribes to backend /reported_data WebSocket feed.
  • Detects changes per DataAttribute and builds event records.
  • Persists selected events into MongoDB for history.
  • Broadcasts each new event to connected UI websocket clients.
Bundle files used
  • Event_list.py (this app)
  • templates/event_list.html (UI template)
  • SS1_HMI_dataset.xlsx (event mapping)
“Event” definition (in this context)
A backend value change becomes an “event” if there is a matching Excel row where Description is present, and the row’s Event_list evaluates to True. Everything else is ignored.
High-level components
  • Backend WS consumer (websockets.connect).
  • Excel mapping filter (pandas).
  • MongoDB persistence (pymongo).
  • UI server endpoints + UI websocket broadcast (FastAPI).
Threading / async model
The FastAPI app starts a background asyncio task via lifespan: subscribe_and_monitor(). That task blocks on backend WS receives and emits DB writes + broadcasts. UI websocket connections are maintained independently.

Backend dependency
This app consumes the backend’s live report stream only:
ws://localhost:8000/reported_data
It assumes the backend provides per-IED and per-RCB nested values with q (quality) and t (timestamp in ms) inside each nested payload.
Backend message shape (expected)
{
  "<IED>": {
    "<RCB_NAME>": {
      "<base_da>": {
        "stVal": 1,
        "q": "...",
        "t": 1730000000000,
        "...": "nested MMS-decoded structure"
      }
    }
  }
}

MongoDB record schema
Records are inserted into TestBedScada.Event_list with _id derived from attribute + timestamp. 
{
  "_id": "<DataAttribute>_<formatted timestamp>",
  "substation": "<Substation>",
  "bay": "<Bay>",
  "device": "<Device>",
  "attribute": "<flattened DataAttribute key>",
  "value": "<raw value>",
  "description": "<Description>",
  "quality": "<nested_val.q or N/A>",
  "timestamp": "<YYYY-MM-DD HH:MM:SS.mmm>",
  "history": true
}
Live broadcast payload
Each inserted Mongo record is broadcast as JSON to UI websocket clients (/ws). The payload is identical to the stored record (same keys).
Timestamp formatting
The app converts backend t (ms epoch) to: YYYY-MM-DD HH:MM:SS.mmm. If conversion fails, timestamp becomes Invalid.
Live event generation flow
  1. Startup creates a background task: subscribe_and_monitor().
  2. Task connects to backend WS: /reported_data.
  3. Each backend message is decoded and flattened into key/value pairs.
  4. Each flattened key is matched against Excel DataAttribute where Description is present.
  5. On value change, a record is created, gated by Excel Event_list.
  6. Record is inserted into MongoDB and broadcast to UI websocket clients.
UI consumption flow
  1. Browser loads GET / (template).
  2. Browser opens WS /ws for live pushes.
  3. Browser may call GET /api/events to load recent history.
  4. Each pushed record is rendered as an event row/card in the UI.
Duplicate handling
Each event record uses _id = DataAttribute + "_" + timestamp. If Mongo rejects insert due to duplicate key, the app silently ignores it (exception swallowed) and continues.
